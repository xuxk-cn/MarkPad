# 📝 高效轻量型 Markdown 编辑器开发方案讨论稿
> **定位**：类 Typora 即时渲染体验，但以**极致响应速度、极低内存占用、功能极简**为第一优先级  
> **适用对象**：核心开发团队、架构评审、产品经理  
> **版本**：v0.1（讨论草案）

---

## 🔍 一、核心设计原则
| 原则           | 说明                                     | 红线指标                                                |
| -------------- | ---------------------------------------- | ------------------------------------------------------- |
| **性能优先**   | 所有架构决策服从输入延迟与内存占用       | 输入响应 ≤ 8ms，常驻内存 ≤ 60MB（Win）/ ≤ 45MB（macOS） |
| **功能做减法** | 仅保留“写作必需”能力，其余一律延后或剔除 | 启动时间 ≤ 0.8s，安装包 ≤ 15MB                          |
| **架构去依赖** | 拒绝重型框架与运行时，能原生实现不引入库 | 无 Electron/React/Vue，无全局状态管理库                 |
| **渲染可预测** | 避免隐式重排重绘，DOM 变更完全受控       | 帧率稳定 ≥ 55fps（长文档滚动）                          |

---

## 🧱 二、技术选型与架构草案
### 1. 运行时与桌面壳
- **推荐方案**：`Tauri v2`（Rust 后端 + 系统 Webview）
  - 优势：二进制体积小、内存占用低（对比 Electron 降 60%+）、原生文件系统 I/O
  - 备选：纯 Rust + `egui`/`slint`（性能更极致，但富文本开发成本呈指数上升，暂不推荐）

### 2. 前端技术栈
- **语言/框架**：TypeScript + 原生 DOM API + `requestAnimationFrame` 调度
- **拒绝项**：React/Vue/Angular、状态管理库（Redux/Zustand）、CSS-in-JS
- **构建工具**：`Vite`（仅用于开发期），生产环境直接 `tsc` + 手动 bundle 压缩

### 3. 解析与渲染架构
```
[键盘/粘贴事件] → [文本缓冲区 (Ring Buffer)] → [增量解析器 (Rust→WASM)] → [AST Diff]
       ↓
[视口计算] → [DOM 片段生成 (DocumentFragment)] → [虚拟滚动容器] → [系统 Webview 渲染]
       ↓
[光标/选区同步] ← [Selection API 拦截] ← [坐标映射表]
```
- **解析器**：初期采用 `markdown-it` 定制增量插件，验证稳定后替换为 Rust 编写的增量 CommonMark 解析器（编译为 WASM）
- **渲染策略**：彻底放弃 `contenteditable`，采用 **虚拟行块 + 懒加载 DOM**，仅渲染可视区及前后 2 屏内容
- **选区管理**：通过 `window.getSelection()` + 坐标偏移映射模拟原生光标，避免浏览器默认行为干扰

## 🚫 三、功能边界定义（MVP 范围）
### ✅ 明确保留（Phase 1 交付）
- 实时所见即所得渲染（输入即渲染，无预览/编辑双栏）
- 基础 Markdown 语法（标题、列表、粗斜体、代码块、引用、链接、图片）
- 本地文件读写（自动保存、UTF-8/GBK 兼容）
- 撤销/重做（≥ 5000 步）、基础快捷键（Ctrl/Cmd + Z/Y/S/B/I 等）
- 系统级深色/浅色模式跟随

### ❌ 明确剔除（不进入 MVP，后续按需评估）
- 云同步/账号系统
- 插件/扩展市场
- 导出 PDF/Word/HTML（仅提供“复制为纯文本/Markdown”）
- 数学公式、流程图、表格可视化编辑
- 多标签页、侧边栏大纲、全局搜索
- 主题自定义、字体渲染微调、打印预览

## 📅 四、开发阶段规划
| 阶段                    | 周期   | 交付物                                        | 验收标准                                    |
| ----------------------- | ------ | --------------------------------------------- | ------------------------------------------- |
| **Phase 1: 核心管道**   | 4~5 周 | 文本缓冲 + 增量解析 + 基础渲染 + 文件 I/O     | 可打开 10MB 纯文本 MD，输入无卡顿           |
| **Phase 2: 性能调优**   | 3~4 周 | 虚拟滚动 + AST Diff + 光标同步 + 内存泄漏排查 | 输入延迟 ≤ 8ms，滚动 5 万行文档帧率 ≥ 50fps |
| **Phase 3: 稳定性打磨** | 2~3 周 | 快捷键、撤销栈、异常边界处理、Tauri 打包裁剪  | 无崩溃，安装包 ≤ 15MB，启动 ≤ 0.8s          |
| **Phase 4: 压测与发布** | 2 周   | 性能报告、自动化测试集、用户试用版            | 通过 100+ 真实文档压测，内存/延迟达标       |

## ⚠️ 五、核心风险与应对预案
| 风险点                             | 影响         | 应对策略                                                     |
| ---------------------------------- | ------------ | ------------------------------------------------------------ |
| 自定义渲染导致光标错位/选区异常    | 体验崩塌     | 初期严格对齐 CodeMirror 6 选区逻辑，编写自动化选区测试集；保留 `contenteditable` 降级开关 |
| WASM 解析器体积/兼容性问题         | 启动慢或崩溃 | 提供纯 JS fallback 解析器；Rust 编译启用 `opt-level=3` + `wasm-opt -Oz`；按需加载 |
| 过度裁剪引发用户流失               | 产品定位模糊 | 建立“性能-体验”评估矩阵，每项新增需通过压测；提供 `--enable-features` 启动参数供高级用户开启 |
| 跨平台 Webview 差异（WebKit/Edge） | 渲染不一致   | 锁定系统 Webview 版本策略；CI 加入 macOS/Windows/Linux 三端视觉回归测试 |

---

## ❓ 六、待团队讨论的关键问题
1. **渲染架构取舍**：是否接受“放弃 contenteditable”带来的开发成本？是否考虑初期基于 `CodeMirror 6` 核心裁剪，快速验证性能天花板？
2. **平台优先级**：首版聚焦 macOS 还是 Windows？Linux 是否同步支持？（影响 Webview 选型与打包策略）
3. **开源与商业化**：采用 MIT/Apache-2.0 开源？还是核心闭源+高级功能付费？是否接受社区 PR？
4. **性能监控机制**：是否内置轻量级遥测（如输入延迟分布、内存水位）？如何平衡隐私与调优需求？
5. **长文档策略**：单文件上限设定为多少？（建议 50MB，超限提示分割或降级渲染）
